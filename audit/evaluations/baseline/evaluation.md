# Native baseline evaluation

**Outcome.** Fixed the synthetic invoice API on dedicated local branch `fix/merchandise-only-discount` in `project/`. No toolkit or skills were read. No existing repository, network, credentials, global configuration, browser, plugins, paid API or GPU was used. No publication or PR was created.

**Diagnosis and investigation.** The original expression discounts `(subtotal + shipping)`, so promotions incorrectly discount shipping. For merchandise 1,000 cents, shipping 200 cents and discount 10%, expected 1,100 cents; original returned 1,080. For merchandise 101 cents, shipping 7 cents and discount 50%, expected 57; original returned 54. The original also accepted negative prices/shipping, zero quantities and percentages over 100. The fix validates each required bound and computes the discounted merchandise subtotal before adding shipping.

**Technical contract.** Keep `invoice_total(items, shipping_cents=0, discount_percent=0)`. Items are an iterable of `(price_cents, quantity)` pairs, with integer cents and positive quantities. For merchandise subtotal S, shipping H and percentage D, return `floor(S * (100 - D) / 100) + H`. Round the aggregate merchandise total once, not each line. Reject any negative price or shipping, quantity <= 0, or percentage outside inclusive 0..100 with `ValueError`. Zero prices, empty invoices, and discounts of 0 and 100 are valid. An empty invoice costs shipping alone; a 100% discount retains shipping. Support single-pass iterable inputs. Integer amounts and integer percentages retain exact integer arithmetic, including large values.

**Interface and impact.** Function name, parameters and defaults are unchanged. Callers see corrected totals whenever shipping and a nonzero discount coexist, and now receive `ValueError` for invalid bounds. No transport, HTTP error mapping, UI, persistence, tax, refund or payment interface was supplied or changed. Validation visits all items even at 100% discount so invalid hidden lines are rejected. Complexity remains O(number of items) time and O(1) auxiliary space. No new dependencies.

**Behavioral evidence.** `python3 -m unittest -v` passed 7 test methods, including 10,201 amount/discount combinations that verify shipping additivity and floor inequalities, fixed expected totals, aggregate rounding, empty input, boundaries, multiple quantities, generator input, large exact integers and nine invalid input cases. Full output: `test-results.txt`. Running three relevant test methods against the original source produced 11 assertion failures and zero errors, demonstrating that the checks detect the initial behavior; details: `regression-control.txt`. `git diff --check` passed.

**Browser assessment.** Not verified. Only a Python function and synthetic request were supplied; there is no checkout build, runnable storefront, URL, browser fixture or transaction test environment. API success cannot establish checkout behavior. Once such an environment exists, the proposed manual check is to apply a promotion with nonzero shipping and verify merchandise discount, rounding, shipping retention and displayed final total against the API; invalid inputs should also be checked through the actual integration's supported entry points.

**Local delivery proposal.** Review `project/invoice.py`, `project/test_invoice.py`, and `invoice-fix.patch`; run `cd project && python3 -m unittest -v`. The patch contains both code and new tests. Changes remain local on the synthetic branch; there is no remote delivery. Integration owners should map the new validation exception at their API boundary and provide a browser build before any checkout claim is made.

**Budget and limitations.** Four experiments: (1) baseline behavioral reproduction and invalid-input probes; (2) complete fixed behavior suite; (3) original-source regression control; (4) diff/whitespace review. Elapsed measured from initial repository inspection to artifact generation: 112.4 seconds, under the 300-second and 8-experiment limits. Initial files were read immediately before timing began. Changed existing file: `project/invoice.py`; added test: `project/test_invoice.py`; evaluation artifacts: this report, `test-results.txt`, `regression-control.txt`, `invoice-fix.patch`. A synthetic Git repository and Python bytecode cache were created locally. Malformed item structures, nonnumeric values and a formal floating-point/fractional-percentage policy are outside this focused change and are not claimed as validated. Tests cover the existing integer-cent domain with integer percentages; no end-to-end browser evidence exists.
